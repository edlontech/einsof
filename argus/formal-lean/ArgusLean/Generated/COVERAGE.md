# ArgusKernel.lean -- extraction coverage (Phase C extraction-refactor, 2026-05-29)

Generated by `argus/scripts/charon-aeneas-extract.sh` from `argus-kernel` via Charon + Aeneas.

**Status: 12/12 transitions transparent; the full model ELABORATES clean in Lean 4.30 (no
`axiom`, no `sorry`, no errors).**

The blocker was never the protocol logic -- it was that Aeneas has **no model for
`BTreeMap`/`BTreeSet` iteration** (the std B-tree iterators extract with missing
`step_by`/`enumerate`/`take` fields), whereas it models `Vec` and its iterator completely. The
fix (Phase 2 of the extraction-refactor, branch `feat/extraction-refactor`) was to replace all
kernel `BTreeMap`/`BTreeSet` state with `Vec`-backed `VecMap`/`VecSet` wrappers
(`src/collections.rs`) whose every traversal is an explicit index `while` loop -- no iterator
adapters, no closures, no early `return` inside loops. With zero B-tree types left, Charon emits
zero B-tree iterators and the whole model goes through.

## What made it extract (hard-won Aeneas constraints)

Encoded in `src/collections.rs` and the transitions:

1. **No `BTreeMap`/`BTreeSet`** -- Aeneas has no iteration model for them. Use `VecMap`/`VecSet`
   (Vec-backed). `Vec` + its `Iterator` impl are fully modelled in the Aeneas Lean library
   (`Std/Vec.lean`, `Std/VecIter.lean`, `Std/Slice.lean`).
2. **Index `while` loops, never `.iter()`/`for`/closures**, and **no early `return` inside loops**
   -- accumulate into a flag/struct and branch *after* the loop (`GateAccum` in `transitions.rs`;
   the flow gates and capability checks were rewritten this way -- this is also what finally made
   `invoke_start`/`return_unendorsed`/`sentinel_elevate_taint` transparent, since their early
   returns-in-loops previously forced an axiom).
3. **No `Vec::is_empty`/`Vec::contains`** in the wrappers (not in Aeneas's Vec model) -- use
   `len() == 0` and hand-rolled scans.
4. **Do not consume the borrow from a computed-index lookup.** `VecMap::get -> Option<&V>` is fine
   for *comparisons* (`get(k) != Some(&x)`) and for a `match` whose `None` arm diverges
   (`None => return Err`), but matching it as an *expression* with value-producing arms and then
   calling a (looping) method on the inner `&V` triggers an Aeneas region-inference internal error.
   So the set-valued queries go through owned/bool accessors: `get_cloned`, `get_set_or_empty`,
   `set_contains`, `set_nonempty`, `any_value_contains`. `BackgroundTheory::tool_metadata` returns
   an **owned** `Option<ToolMetadata>` for the same reason.
5. **Named key structs, not tuples** (`OverrideKey`, `FlowKey`, `OverrideEntry`) -- Aeneas cannot
   resolve the tuple "Pair" comparison.
6. **Payload-free `KernelError`**, **owned `CapKind::ALL`** (index-loop, not array `IntoIter`),
   `match` instead of `is_some_and`/`unwrap_or`/`cloned`/`?`-on-`ok_or` in extracted bodies.

Test code (`#[cfg(test)]`, `tests/`) is **not** extracted (not reachable from the Charon entry
points `crate::transitions` + `crate::state::_::initial`), so it freely uses `VecSet::from([..])`,
`FromIterator`, `.iter()`, and the `is_some_and`/`map_or` combinators.
